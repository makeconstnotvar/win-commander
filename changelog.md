- Remote connections now record what actually happened to them (Q2-5, RC-11). Everything built for retry policy, failure classification and scheduling had been reasoning about outcomes nobody produced; the place where a connection really succeeds or fails now records it, filed under the connection's own identifier. Nothing about existing behaviour changes: whatever the connection attempt returns is returned and whatever it raises is raised again, after being recorded, so every screen that already depends on that path behaves exactly as before. A cancelled password prompt is not recorded as a failure - nothing was ever asked of the server, and treating it as one would spend a retry budget and eventually mark a connection blocked because somebody pressed Cancel. An error nobody can name is recorded as one that must not be retried. With this, a refused host key travels the whole way from the handshake to a connection marked blocked with no retry armed. Focused tests pass 8/8 with 31 assertions and `WinCommanderUT` 812/812 with 11,796.
- "Open terminal here" and "open in editor" now have a decided shape (Q2-9, TL-2). The rule for which directory a local tool may be pointed at existed; this turns it into a launch. The location is checked before the configured application is even looked at, and the ordering is the decision: a missing editor is a visible failure someone can fix in settings, while a path inside an archive resolves silently against the real filesystem and opens the wrong place, so that is the refusal that must be reached when both are wrong. The application and its arguments are kept separate rather than composed into a command line, so a filename containing a semicolon, a quote or a newline stays a filename. A terminal is opened at the directory and given no files, because "here" is the one thing that command promises and a selection would make it mean something else. A selection that no longer belongs to the open directory is dropped, since selections outlive the listings they came from and that is how a stale one edits the wrong file - and containment is by path component, so a folder named `project-other` is not inside `project`. Being unconfigured is reported differently from being configured with nonsense, so the user is not sent to the wrong place to fix it. Focused tests pass 8/8 with 25 assertions and `WinCommanderUT` 804/804 with 11,765. Performing the launch is still to come.
- A network volume can now be asked whether it is still there, without the answer costing a stall (Q2-7, NW-3). Whether a server still responds is the one fact that cannot be had without touching it, and touching it is what this model keeps away from the thread that draws. There is no timeout on the underlying system call - under a dead mount the kernel holds it for tens of seconds and nothing can interrupt it - so the deadline is on the wait rather than the call: it runs on a thread of its own and is abandoned when the budget is spent, owning everything it touches so its eventual return is harmless. A reply arriving after the budget does not retract the verdict, because something that takes half a minute to answer is exactly what must not go on the drawing thread. Silence and refusal are kept apart: a server that answers "no such export" fails fast and can be refused up front, while one that says nothing blocks. Answers are remembered so drawing a row never probes, but they expire, because a reassuring answer from a minute ago would hide a mount that has died since. The probe itself runs outside the lock, so a stuck one cannot block reads - a test holds a probe open and checks exactly that. Focused tests pass 7/7 with 42 assertions, 15/15 with 93 under the thread sanitizer, and `WinCommanderUT` 796/796 with 11,740.
- Network volume state now has something to read it from (Q2-7, NW-2). The rule that an unresponsive network mount must never be touched from the drawing thread was decided earlier, but nothing produced the facts it reasons about. The mount table is read without asking the kernel to refresh each filesystem's statistics, because that makes the call wait on every mount in turn and a server that has gone away will not answer - so the very call meant to discover unresponsive volumes would hang on one. Whether a volume is on the network comes from the kernel's own flag rather than a list of filesystem names, which would go stale the moment a new one appears and would then report an unrecognised network volume as local. A path is matched to its volume by path component and never by string prefix, so `/Volumes/data` cannot claim `/Volumes/database`. A path that cannot be placed on any volume is reported as unplaceable rather than guessed at: the first version returned facts that the classifier reads as "local", which means "safe to touch while drawing" for exactly the path nobody could account for, and the test caught it. Focused tests pass 8/8 with 58 assertions, one of them against the real mount table, and `WinCommanderUT` 789/789 with 11,698.
- Git status is now actually read from a repository (Q2-9, GT-3). Finding the repository and parsing the output both existed; between them sat launching the process, and the launch is where the decisions are. git is never run through a shell - a repository path can contain spaces, quotes, semicolons and newlines, and a command line would let all of them be read as syntax; a test creates a repository named with exactly that and reads it. That test caught the flaw in its own fixture helper first, which was pasting the directory into a shell command and broke on the quote. Every `GIT_*` variable is stripped from the child's environment, because one inherited from whoever launched the application would silently point git at a different repository and every badge would describe someone else's working tree. The refresh does not take the index lock, so a background redraw cannot fight the git command the user typed themselves, and git is given no way to ask a question, since a credential prompt would block the refresh forever. A repository that takes too long or produces too much is reported rather than truncated, because a partial status looks exactly like a clean tree for the paths it leaves out. Seven tests against real git and real repositories pass with 42 assertions, sixteen with 67 under the address sanitizer, and `WinCommanderUT` 781/781 with 11,640. The project's stack-frame check caught an oversized buffer in this code, and separately, two unrelated tests are over that limit in a way that blocks the sanitizers from building the suite at all - spun off as its own task.
- Git badges can now tell which repository a folder belongs to (Q2-9, GT-2). The status parser could already read a repository's state; nothing could say whose state to read. The walk up to the repository root is short, and the refusals are the substance: a `.git` that is a file rather than a directory is accepted, because linked worktrees and submodules both look like that and rejecting them would silently attribute a submodule's files to the enclosing repository, whose status never mentions them; the nearest repository wins for the same reason. The walk stops at a filesystem boundary, as git itself does, so a volume mounted inside a checkout does not inherit that checkout's status - while a repository beginning exactly at a mount point is still found. A directory that cannot be read ends the walk rather than being stepped over, since continuing would mean crossing a boundary nobody checked. A relative path is refused rather than resolved against the process's own working directory, which would answer confidently about somewhere else entirely, and a dangling `.git` symlink is not accepted as a marker. Focused tests pass 9/9 with 25 assertions, two of them against the real filesystem, and `WinCommanderUT` 774/774 with 11,598.
- The reconnect loop now exists (Q2-5, RC-10). Three decisions had been built with no caller - whether a failure may be retried, what a failure actually was, and when the next attempt is due - and this is the piece that asks them in order: claim what is due, attempt it, classify the outcome, record it. It owns no timer, so a caller arms one from the deadline it reports and the tests run against a supplied moment rather than real elapsed time. A connection is never attempted twice within one pass, which matters when a fresh backoff lands in the past: without that rule the loop would keep re-claiming the same connection and hammer a server that is plainly not answering. A connector that throws is recorded as unretryable, because our own broken code is not evidence that the server will answer next time. One test carries a refused host key all the way from the connector through classification to a retry that is never armed and never picked up again - the end of the chain built over the last several changes. Focused tests pass 6/6 with 43 assertions and `WinCommanderUT` 765/765 with 11,573. No production caller yet: wiring it into the connection manager is the next step.
- Reconnect scheduling now has somewhere to live (Q2-5, RC-9). A registry owns the state of every known remote connection and, when one fails in a way worth retrying, arms an absolute deadline computed once - a delay recomputed on every tick would restart the wait each time anybody asked, and the connection would sit "about to retry" forever without ever coming due. Due connections are handed out and disarmed in the same locked step rather than merely reported: two ticks that both saw the same one would each start an attempt, and the second would race the first against a server that is already having trouble. A success, an explicit disconnect, a failure that must never be retried, and a spent budget all leave nothing armed. Eight threads claiming sixty-four due connections hand out exactly sixty-four. Focused tests pass 8/8 with 51 assertions, also under the thread sanitizer, and `WinCommanderUT` 759/759 with 11,530. Running that sanitizer turned up a pre-existing blocker unrelated to this work: one test's stack frame is large enough that the sanitizer's instrumentation pushes it past the project limit, so the whole unit-test suite fails to build under it. That is spun off separately.
- Remote failures are now classified into the vocabulary the retry policy reasons about (Q2-5, RC-8). The policy deciding which failures may be retried automatically has been correct since RC-1, but nothing produced its terms from a real error, so none of its decisions could ever be reached. This closes the loop opened by host verification: a server whose key is refused now arrives at the retry policy as a verification failure, which is never retried - without that hop a reconnect timer would go on reaching a server whose identity failed to check out, which is exactly what verification exists to prevent. Anything the classifier cannot name is treated as unretryable, because retrying a failure nobody can name is how a connection ends up hammering a server for reasons no one understands. A rejected credential is kept apart from a permission refusal: both mean no, but one sends the user to replace a credential and the other says the account may not do this, and collapsing them would send someone to change a password that works. Focused tests pass 6/6 with 38 assertions and `WinCommanderUT` 751/751 with 11,479. Nothing calls it yet - the connect paths still return raw errors, and feeding them in is the reconnect-scheduler step this unblocks.
- The compress dialog now lets you choose the archive format (Q2-6, AR-3). The menu is built from the same model the engine reads rather than listed in the dialog file, so it cannot come to offer a format the engine does not produce. Choosing brings a rule with it: only zip can carry a passphrase, which is now recorded as a fact about the format instead of knowledge spread across the code. Picking a format that cannot encrypt withdraws password protection rather than leaving a ticked box that would produce an unprotected archive, and what was typed stays in the field so coming back to zip does not ask for it again - though protection is not silently switched back on either. Building the dialog for real in a test caught something no amount of reading would have: disabling the checkbox by setting its enabled flag did not stick, because a control whose value is bound has that flag managed for it, and the assignment was overwritten by the very next line. It would have shipped as a checkbox that stayed clickable for tar, letting someone tick it and receive an unprotected archive. The dialog suite passes 2/2 with 24 assertions, the format model 8/8 with 47, and the whole compression suite 19/19 with 308, also under ASAN+UBSAN.
- The compression engine can now create every format the application says it can (Q2-6, AR-2). Until now it produced exactly one - zip, hardcoded, with `.zip` appended to every filename it generated - so the set of formats described in the model was a choice nothing could act on. The format model moved down into the operations layer, where the code that actually writes archives lives, because two copies of that table would eventually disagree and the picker would offer a format the engine could not produce. Tar, tar.gz and tar.bz2 share one container, chosen so a tarball carries the ownership and permission metadata those formats are picked for without becoming unreadable to plain `tar`. A passphrase asked of a format that cannot carry one is now refused outright rather than quietly dropped: producing the tarball anyway would leave an archive that looks finished while nothing says its contents are readable by anyone who gets the file. Each format is created and then read back in the tests, including the directory nesting, since a wrong container would still have produced a file with the right name. The compression suite passes 17/17 with 284 assertions, plainly and again under ASAN+UBSAN and under TSan. Choosing the format in the compress dialog is still to come.
- SFTP now verifies the server's identity before it authenticates (Q2-5, RC-6/RC-7). Until now the handshake completed and authentication began no matter what key the server presented, including a key that had changed since the last connection - so the host-trust rules built earlier were correct and consulted by nobody. The check runs immediately after the handshake and before every authentication path, because a password or a passphrase-unlocked key sent to an unverified server is already disclosed and refusing afterwards would only report an interception that had already worked. A pinned host connects without interruption; an unknown one asks once, showing host, port, algorithm and fingerprint, and is remembered on acceptance; a host whose key has changed is refused without a prompt, since offering accept/decline there would train people to click through the one warning that must never become routine. An accepted host whose pin could not be stored is reported as a refusal rather than connected anyway, because otherwise the next launch would ask again and leave no way to tell an unremembered host from a changed one. Pins are filed under the host and port together, in OpenSSH's bracketed spelling, so two services on one machine cannot inherit each other's identity and IPv6 addresses cannot be confused with a host-and-port pair. A build with no policy installed refuses to connect rather than falling back to connecting unverified. Focused suites pass 6/6 and 8/8; `WinCommanderUT` passes 751/751 with 11,475 assertions and `VFSUT` 191/191.
- Added the crash-cleanup sweep for Q2-10 (RH-6): it removes leftovers of an interrupted write from the target's own directory and reports what it removed and what it could not, rather than tidying silently. It never recurses, since a leftover is created beside its target; it checks the link status rather than resolving it, because a symlink wearing that name was not written by us and following one would let a planted link redirect the deletion elsewhere; and it never throws, since best-effort cleanup at startup must not stop the application from starting. Two latent traps surfaced on the way: a symlink test broke the *following* test rather than itself, because the shared temp-directory cleanup handled files and directories but not symlinks, which the physical-walk mode always reports separately — so the link survived, its directory could not be removed, and the next test failed in its own constructor with a message pointing nowhere near the cause. The production code already handled this correctly; only three test harnesses did not, and all three are fixed. `WinCommanderUT` passes 743/743 with 11,439 assertions, `BaseUT` 80/80, `PanelUT` 57/57 and `UtilityUT` 121/121.
- Made interrupted atomic writes identifiable for Q2-10 (RH-5): if the process dies between creating the temporary and renaming it, that file survives forever and accumulates one per crash in the user's own directory. - Fixed a durability defect in `nc::base::WriteAtomically` for Q2-10 (RH-1): it wrote through a temporary and published with `rename`, so replacement was atomic, but it flushed neither the file before the rename nor the parent directory after it. Without the first, a crash can leave a correctly named file holding garbage — worse than losing the write, since nothing downstream can tell; without the second, the rename can roll back and the file silently reverts while the call has already reported success. Both `Config` and `FileOverwritesStorage` write through this function, and the latter exists to detect external modification, so losing its write silently is how the app would later overwrite a user's changes believing nothing had changed. The two barriers are handled asymmetrically on purpose: a failed file flush aborts and rolls back, while a failed directory flush does not, because the rename has already succeeded and undoing a completed publication would turn a durability question into certain data loss. `F_FULLFSYNC` is deliberately not used, since this function runs on arbitrary paths including network and removable volumes where the barrier can be acknowledged without stable persistence. `BaseUT` passes 80/80 cases with 70,576 assertions and `ConfigUT` 38/38. See [`atomic_write_durability_fix.md`](Docs/Features/atomic_write_durability_fix.md).
- Added the creatable-archive-format model for Q2-6 (AR-1), closing a real gap: extraction support already existed as a whitelist inside an action, but creation support was modelled nowhere — and the two are genuinely different sets, since RAR and others extract but cannot be created. A surface treating them as one would offer a Create entry that fails only after the user has picked a format and named a file. Extension resolution takes the longest match, so `backup.tar.gz` resolves to gzipped tar rather than a bare gzip stream; that failure is the quiet kind, producing a file named like a tarball that opens to a single unnamed blob with the archived directory structure silently absent. Dotfiles are not treated as archives, and the model records the trade-off that makes multiple formats worth offering at all — tar-based formats carry POSIX ownership and permissions, zip does not, and plain tar does not compress. Focused tests pass 6/6 cases with 34 assertions; full `WinCommanderUT` passes 733/733 cases with 11,384 assertions. - Added network volume state classification for Q2-7 (NW-1), completing that row's third item: the rule it exists for is that an unresponsive network mount must never be touched from the drawing thread, because a `stat()` under a dead NFS or SMB mount does not fail but blocks until the kernel's own timeout — tens of seconds — which is precisely how a file manager becomes a beachball. The state therefore has to be known before the access rather than discovered by making it.
